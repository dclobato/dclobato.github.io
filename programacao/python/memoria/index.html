    Gerenciamento de memória¶

    Em Python, o programador não precisa reservar nem liberar memória: quando um objeto é criado, o interpretador reserva o espaço necessário, e, quando o objeto deixa de ser usado, o espaço é liberado automaticamente. Esse gerenciamento automático evita uma série de erros, como esquecer de liberar a memória ou usar uma área que já foi liberada. Mas entender como ele funciona ajuda a escrever programas que usam menos memória, a entender o comportamento das variáveis e a evitar algumas surpresas.

    Nomes, objetos e referências¶

    Em Python, tudo é objeto: números, cadeias de caracteres, listas, funções, classes. Uma variável não é uma "caixa" que guarda um valor, mas um nome que aponta para um objeto, ou seja, uma referência ao objeto. Vários nomes podem apontar para o mesmo objeto, e um objeto pode ser apontado também por elementos de listas, valores de dicionários e atributos de outros objetos.

    Cada objeto tem uma identidade, que não muda enquanto ele existe e que pode ser consultada com a função id(). O operador is verifica se dois nomes apontam para o mesmo objeto, enquanto == verifica se os dois objetos têm o mesmo valor:

    Nesta execução do CPython, os valores 1000 e as cadeias "programa" iguais foram representados por objetos distintos. Já alguns objetos imutáveis, como os inteiros de -5 a 256, são reaproveitados nessa implementação. A identidade de valores iguais depende de otimizações: não conte com um objeto novo nem compartilhado. Use == para comparar valores; is verifica identidade e é a escolha para x is None.

    A seção sobre passagem de parâmetros mostra as consequências desse modelo nas chamadas de funções: o parâmetro passa a ser mais um nome para o objeto passado como argumento.

    Onde ficam os objetos: o heap privado e a pilha¶

    O modelo abaixo descreve o CPython, com um diagrama simplificado dos objetos e das chamadas. Alocadores, contagem de referências e tamanhos em bytes são detalhes da implementação, não garantias da linguagem. As medições variam com a versão, a arquitetura e a configuração do interpretador.

    • O heap privado contém os objetos e seu armazenamento associado. O gerenciador de memória combina alocadores e caches. Na configuração tradicional do CPython, pymalloc atende pequenas alocações, de até 512 bytes, usando arenas; pedidos maiores seguem para o alocador do sistema, sem necessariamente pedir memória nova ao sistema operacional a cada chamada. No CPython 3.14 com execução sem GIL (free-threaded), os domínios de objetos e memória usam mimalloc. A documentação dos alocadores detalha essas configurações;
    • A pilha de chamadas representa as funções em execução e seu estado local. Frames podem continuar acessíveis após o retorno, por exemplo por um traceback; geradores também preservam estado entre chamadas. O diagrama é conceitual e não especifica a disposição física dessas estruturas na memória.

    O diagrama mostra um programa que chamou uma função dobro(n). Os quadros da pilha guardam apenas nomes; os objetos, inclusive os números, ficam todos no heap.     Contagem de referências¶

    No CPython, o mecanismo principal é a contagem de referências, complementada por um coletor de ciclos. Em objetos comuns, criar referências aumenta a contagem e removê-las a diminui. Ao chegar a zero, o objeto normalmente é finalizado e seu armazenamento pode ser reaproveitado. Há exceções e otimizações: objetos imortais, como alguns inteiros pequenos, não seguem uma contagem comum, e configurações sem GIL podem adiar a recuperação. Outras implementações de Python podem usar mecanismos diferentes.

    sys.getrefcount(obj) permite observar a contagem no CPython, normalmente incluindo uma referência temporária do argumento. O número não deve orientar a lógica do programa, especialmente para objetos imortais. O exemplo usa __del__ para observar a finalização na configuração tradicional; não há garantia geral de execução imediata desse método. Para liberar arquivos e outros recursos no momento certo, use with, em vez de depender de __del__.

    import sys


class Ponto:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __del__(self):
        print(f"Ponto({self.x}, {self.y}) liberado")


p = Ponto(1, 2)
print("referências:", sys.getrefcount(p) - 1)   # -1: o próprio argumento conta

q = p                                            # outro nome para o mesmo objeto
lista = [p]                                      # a lista também guarda uma referência
print("referências:", sys.getrefcount(p) - 1)

del q
lista.clear()
print("referências:", sys.getrefcount(p) - 1)

print("removendo o último nome...")
del p
print("fim do programa")

    referências: 1
referências: 3
referências: 1
removendo o último nome...
Ponto(1, 2) liberado
fim do programa

    Repare que del p não apaga o objeto: ele apaga o nome p. O objeto só foi liberado porque aquele era o último nome que apontava para ele; se ainda houvesse outra referência (em q ou na lista), o objeto continuaria existindo.

    O coletor de lixo e os ciclos¶

    A contagem de referências tem um ponto fraco: os ciclos. Se o objeto A aponta para o objeto B, e B aponta para A, cada um mantém a contagem do outro acima de zero, mesmo que nenhuma parte do programa consiga mais acessar nenhum dos dois. Para esses casos, o interpretador tem um coletor de lixo (garbage collector), que é executado periodicamente, procura grupos de objetos que só são referenciados uns pelos outros e os libera. O módulo gc permite controlá-lo e executá-lo manualmente:

    import gc


class No:
    def __init__(self, nome):
        self.nome = nome
        self.outro = None

    def __del__(self):
        print(f"{self.nome} liberado")


a = No("A")
b = No("B")
a.outro = b
b.outro = a                  # ciclo: A aponta para B, e B aponta para A

del a, b                     # nenhum nome aponta mais para eles...
print("depois do del")       # ...mas cada um ainda é referenciado pelo outro
coletados = gc.collect()     # o coletor de lixo encontra o ciclo
print("objetos coletados:", coletados)

    depois do del
A liberado
B liberado
objetos coletados: 2

    Depois do del, os dois objetos continuaram existindo ("depois do del" foi escrito antes das mensagens de liberação), porque um mantinha o outro. Eles só foram liberados quando o coletor de lixo foi executado. Na prática, não é preciso chamar gc.collect(): o coletor é executado automaticamente, de tempos em tempos, conforme objetos são criados. Mas os ciclos fazem a memória ser liberada mais tarde, e estruturas com muitas referências cruzadas (como grafos em que cada nó aponta para os vizinhos) dão mais trabalho ao coletor.

    Quanto ocupam os objetos¶

    A função sys.getsizeof(obj) informa o tamanho direto atribuído ao objeto, sem somar recursivamente os objetos referenciados nem todo o custo do alocador. Os valores abaixo são de uma execução específica do CPython em 64 bits. print(sys.getsizeof({}), sys.getsizeof(set()))

v = []
anterior = sys.getsizeof(v)
print(len(v), anterior)
for i in range(20):
    v.append(i)
    atual = sys.getsizeof(v)
    if atual != anterior:
        print(len(v), atual)

    • Um número inteiro pequeno ocupa 28 bytes, e os inteiros crescem conforme a quantidade de dígitos (limitados pelos recursos disponíveis). Um float ocupa 24 bytes;
    • Uma cadeia de caracteres vazia ocupa 41 bytes, e cada letra sem acento acrescenta 1 byte. Cadeias com caracteres fora da tabela ASCII, como as letras acentuadas, usam uma representação interna diferente, com um cabeçalho maior (repare nos 61 bytes de "á"), e caracteres como os emojis ocupam até 4 bytes cada;
    • Uma lista guarda apenas referências (8 bytes cada) para os elementos, que são objetos separados. sys.getsizeof conta só as referências, e não os objetos apontados;
    • As últimas linhas mostram como uma lista cresce: em vez de aumentar a cada append, ela reserva espaço extra de vez em quando (com 1, 5, 9 e 17 elementos, no exemplo). Por isso, acrescentar elementos ao final de uma lista custa \(O(1)\) amortizado.

    Economizando memória¶

    Na maior parte dos programas, a memória não é um problema. Mas, em problemas com milhões de valores, como em algumas competições de programação, ela pode fazer diferença.     import array
import sys
import tracemalloc

tracemalloc.start()
lista = list(range(1_000_000))
atual, pico = tracemalloc.get_traced_memory()
print(f"lista de 1 milhão de int: {atual / 1e6:.1f} MB")
print(f"  só as referências: {sys.getsizeof(lista) / 1e6:.1f} MB")
del lista

tracemalloc.reset_peak()
inicio, _ = tracemalloc.get_traced_memory()
arr = array.array("i", range(1_000_000))
atual, _ = tracemalloc.get_traced_memory()
print(f"array('i') de 1 milhão: {(atual - inicio) / 1e6:.1f} MB")
del arr

inicio, _ = tracemalloc.get_traced_memory()
tracemalloc.reset_peak()
total = sum(i * i for i in range(1_000_000))
_, pico = tracemalloc.get_traced_memory()
print(f"soma com gerador: pico de {(pico - inicio) / 1e3:.1f} kB")

    lista de 1 milhão de int: 40.0 MB
  só as referências: 8.0 MB

    • Uma lista com 1 milhão de inteiros ocupou cerca de 40 MB: 8 MB para as referências e o restante para os objetos int, cada um com cerca de 32 bytes;
    • O módulo array guarda os números diretamente, sem criar um objeto para cada um. Um array.array("i", ...) guarda inteiros de 4 bytes, e o mesmo milhão de números ocupou cerca de 4 MB, dez vezes menos. Em troca, ele só aceita valores do tipo indicado. A largura de cada elemento depende da plataforma: consulte itemsize, especialmente para códigos como "i" e "q";
    • Um gerador produz os valores um de cada vez, sem guardá-los: a soma dos quadrados de 1 milhão de números foi calculada com um pico de menos de 1 kB de memória. Sempre que os valores forem usados uma única vez, prefira sum(x * x for x in ...) a sum([x * x for x in ...]), que monta a lista inteira antes de somar.

    A última medição usa uma expressão geradora, a mesma forma apresentada na comparação entre compreensão de lista e expressão geradora. Lá, os exemplos mostram como sum() consome esses valores, a relação com yield e quando vale a pena guardar os resultados em uma lista para reutilizá-los.

    Libere o que não usa mais

    Como a liberação depende das referências, uma estrutura grande continua ocupando memória enquanto houver um nome apontando para ela, mesmo que ela não seja mais usada. Em funções, isso raramente é um problema, porque os nomes locais deixam de existir quando a função termina. No nível do módulo, use del para apagar o nome de uma estrutura grande que não será mais usada, ou, melhor ainda, organize o programa em funções, como mostra a seção sobre módulos.

    Gerenciamento de memória em C, C++ e Python¶

    Todo programa precisa de memória para guardar os seus dados, e toda memória que deixa de ser usada precisa, em algum momento, ser devolvida. As três linguagens deste texto resolvem esse problema de formas muito diferentes, e cada forma tem consequências para a velocidade dos programas, para a quantidade de memória que eles usam e para os erros que o programador pode cometer:

    • Em C, o controle é totalmente manual: o programador pede memória com malloc e a devolve com free;
    • Em C++, o controle continua nas mãos do programador, mas é automatizado pelo escopo: objetos que são donos de memória, como std::vector e std::unique_ptr, a liberam sozinhos quando deixam de existir, e;
    • Em Python, o gerenciamento é totalmente automático: o interpretador cria os objetos, conta quantas referências apontam para cada um e os libera quando ninguém mais os usa.

    Esta página compara as três abordagens. Os detalhes de cada uma estão nas páginas Ponteiros e memória (C), Ponteiros, referências e memória (C++) e Gerenciamento de memória (Python).

    Comparação lado a lado¶

    Característica C C++ Python
    Modelo principal Manual: malloc/calloc/realloc e free Híbrido: liberação automática pelo escopo (RAII, contêineres e ponteiros inteligentes), além de new/delete Automático: contagem de referências e coletor de lixo
    Onde ficam os dados O programador decide: pilha (variáveis locais), memória estática (globais e static) ou heap (alocação dinâmica) O programador decide, como em C; os contêineres guardam os elementos no heap O programador não decide: os nomes ficam nos quadros da pilha de execução, e todos os objetos ficam no heap privado do interpretador
    Quando a memória é liberada No momento exato do free No momento exato em que o dono sai de escopo (fim do bloco, da função ou do objeto que o contém) Quando a contagem de referências chega a zero; objetos em ciclos, quando o coletor de lixo é executado
    Custo extra de memória Mínimo: os próprios dados, mais um pequeno cabeçalho por bloco alocado Mínimo, como em C (um pouco mais para std::shared_ptr) Alto: cada valor é um objeto completo, com tipo e contagem de referências
    Um milhão de inteiros 4 MB (arranjo de int) 4 MB (std::vector<int>) Cerca de 40 MB (lista de int); 4 MB com array.array("i")
    Erros típicos Vazamentos, ponteiros pendentes, liberação dupla, acesso fora dos limites Os mesmos de C, quando se usa new/delete diretamente; ciclos de std::shared_ptr Uso excessivo de memória por referências esquecidas; ciclos que demoram a ser coletados
    O que acontece em um erro Comportamento indefinido: valores sem sentido, Segmentation fault, ou o programa "funciona" Igual a C, para os erros de memória Uma exceção, com mensagem clara (IndexError, por exemplo); não há ponteiros pendentes
    Ferramentas de diagnóstico -fsanitize=address, valgrind -fsanitize=address, valgrind tracemalloc, sys.getsizeof, módulo gc

    #include <stdio.h>
#include <stdlib.h>

typedef struct {
    int id;
} Recurso;

Recurso *cria(int id)
{
    Recurso *r = malloc(sizeof *r);
    if (r == NULL) {
        exit(EXIT_FAILURE);
    }
    r->id = id;
    printf("recurso %d criado\n", id);
    return r;
}

void libera(Recurso *r)
{
    printf("recurso %d liberado\n", r->id);
    free(r);
}

int main(void)
{
    Recurso *a = cria(1);
    {
        Recurso *b = cria(2);
        printf("fim do bloco\n");
        libera(b);              // sem esta linha, o recurso 2 vazaria
    }
    printf("fim de main\n");
    libera(a);
    return 0;
}

    #include <iostream>
#include <memory>

struct Recurso {
    int id;
    explicit Recurso(int i) : id(i) { std::cout << "recurso " << id << " criado\n"; }
    ~Recurso() { std::cout << "recurso " << id << " liberado\n"; }
};

int main()
{
    auto a = std::make_unique<Recurso>(1);
    {
        auto b = std::make_unique<Recurso>(2);
        std::cout << "fim do bloco\n";
    }                           // b sai de escopo: o recurso 2 é liberado aqui
    std::cout << "fim de main\n";
    return 0;
}                               // a sai de escopo: o recurso 1 é liberado aqui

    Em Python, a penúltima linha é fim do programa.

    • Em C, cada recurso só é liberado porque o programa chama libera explicitamente. Se a chamada for esquecida, a memória fica ocupada até o fim do programa (um vazamento); se for feita duas vezes, ou se o recurso for usado depois dela, o resultado é imprevisível;
    • Em C++, a liberação acontece sozinha, no fechamento do bloco: quando a variável b deixa de existir, o destrutor do std::unique_ptr libera o recurso. Esse princípio, de amarrar a vida de um recurso à vida de um objeto, chama-se RAII (Resource Acquisition Is Initialization). O programador não chama nenhuma função de liberação, mas o momento da liberação continua exato e previsível, e;
    • Em Python, o recurso 2 é liberado quando a função termina, porque o nome b era a única referência a ele e a contagem caiu a zero. O recurso 1 é liberado quando o interpretador encerra. O programador não controla, e normalmente nem precisa saber, quando isso acontece.

    Vantagens e custos de cada abordagem¶

    C oferece o máximo de controle e o mínimo de custo: não há nenhum mecanismo rodando por trás do programa, e cada byte usado foi pedido explicitamente. Por isso, C é a linguagem dos sistemas operacionais, dos sistemas embarcados e das bibliotecas de alto desempenho. O preço é que toda a responsabilidade é do programador, e os erros de memória estão entre os mais difíceis de encontrar: o programa pode funcionar nos testes e falhar só em uma situação específica, ou em outro computador. Os acessos fora dos limites, que a linguagem não verifica, são também uma das principais fontes de falhas de segurança em programas.

    C++ mantém o controle e o desempenho de C, mas permite que a liberação seja feita automaticamente pelos objetos donos da memória. Usando contêineres como std::vector e ponteiros inteligentes como std::unique_ptr, em vez de new e delete, a maior parte dos vazamentos e das liberações duplas simplesmente não acontece. Ainda é preciso pensar em quem é o dono de cada recurso: com std::shared_ptr, que libera o objeto quando o último dono deixa de existir, dois objetos que apontam um para o outro formam um ciclo que nunca é liberado, a menos que um dos lados use std::weak_ptr. E referências ou ponteiros comuns para objetos que já foram destruídos continuam sendo um erro possível.

    Python tira o gerenciamento de memória das mãos do programador: não há como esquecer um free, liberar algo duas vezes ou acessar memória inválida, e isso torna o desenvolvimento mais rápido e os programas mais seguros. O custo aparece em memória e em tempo. Cada valor, mesmo um número pequeno, é um objeto completo, com dezenas de bytes, e uma lista guarda referências para objetos espalhados pelo heap. Manter as contagens de referências atualizadas tem um custo a cada operação, e o coletor de lixo é executado periodicamente para encontrar ciclos. Na implementação padrão da linguagem (o CPython), a liberação pela contagem de referências acontece imediatamente; em outras implementações, ela pode acontecer só quando o coletor de lixo for executado.

    Qual escolher?¶

    Não existe uma abordagem melhor em todos os casos. Uma forma de resumir:

    • C, quando é preciso controlar cada byte e cada instrução: sistemas embarcados, sistemas operacionais, dispositivos com pouca memória, bibliotecas usadas por outras linguagens;
    • C++, quando é preciso o desempenho e o baixo consumo de memória de C, mas com uma forma mais segura e mais produtiva de gerenciar os recursos: jogos, aplicações de alto desempenho, programação competitiva, e;
    • Python, quando a produtividade de quem escreve o programa importa mais do que a eficiência no uso da memória e do processador: automação, análise de dados, protótipos, aplicações web, ensino.

    Na prática, as três convivem: muitas bibliotecas usadas em Python, como as de computação numérica, são escritas em C ou C++, justamente para combinar a facilidade de uma linguagem com a eficiência da outra.

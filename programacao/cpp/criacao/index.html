    A criação de um programa em C++¶

    Quando escrevemos um programa em C++, o código que criamos, geralmente salvo em arquivos com extensão .cpp (os arquivos fonte) e .h ou .hpp (os arquivos de cabeçalho), não pode ser executado diretamente pelo computador.

    A razão disso é que o processador só entende instruções em linguagem de máquina, um código binário bem diferente das palavras e comandos que usamos em C++, como std::cout ou int. O processo de compilação é justamente o que transforma esse código legível por humanos em algo que o computador pode executar.

    Para transformar arquivos com o código fonte em um programa que possa ser executado pelo computador, precisamos passar por quatro etapas: edição do código fonte, pré-processamento, compilação e montagem, e link-edição. O programa executável só existe depois que a última etapa é concluída.

    Antes de discutir cada etapa, vamos ver como é um programa completo em C++.

    O primeiro programa¶

    O programa abaixo é o tradicional "Olá, mundo!": ele apenas escreve uma mensagem na tela.

    #include <iostream>

int main()
{
    std::cout << "Olá, mundo!\n";

    Mesmo sendo curto, ele já mostra a estrutura que todo programa em C++ vai ter:

    • Linha 1: #include <iostream> pede que o conteúdo do arquivo de cabeçalho iostream seja incluído no programa. É nele que estão declarados os recursos de entrada e saída de dados, como o std::cout. Os cabeçalhos da biblioteca padrão de C++ não têm extensão: escrevemos <iostream>, <string> e <vector>, e não <iostream.h>;
    • Linha 3: int main() define a função principal. Todo programa em C++ tem exatamente uma função main, e a execução sempre começa por ela. O int indica que ela devolve um número inteiro para o sistema operacional ao terminar;
    • Linhas 4 e 7: as chaves { e } delimitam o corpo da função, ou seja, as instruções que ela executa;
    • Linha 5: std::cout é o fluxo de saída padrão (normalmente, a tela). O operador << "envia" o que está à direita para o fluxo. O \n no fim da cadeia de caracteres faz o cursor pular para a próxima linha, e o ponto e vírgula encerra a instrução, e;
    • Linha 6: return 0; encerra a função main e informa ao sistema operacional que o programa terminou sem erros. Qualquer valor diferente de zero costuma indicar que algo deu errado.

    Espaços de nomes (namespace)¶

    O prefixo std:: que aparece antes de cout indica que cout pertence ao espaço de nomes (namespace) std, onde ficam todos os recursos da biblioteca padrão de C++. Um espaço de nomes funciona como um sobrenome: em uma turma com dois "João", chamamos um de "João Silva" e o outro de "João Souza" para não haver confusão. Da mesma forma, duas bibliotecas diferentes podem ter funções com o mesmo nome, desde que estejam em espaços de nomes diferentes. O operador :: (resolução de escopo) é o que liga o "sobrenome" ao nome.

    Escrever std:: o tempo todo pode parecer cansativo, e por isso é muito comum encontrar programas que começam com a linha using namespace std;. Ela faz com que todos os nomes do espaço std possam ser usados sem o prefixo: cout em vez de std::cout, string em vez de std::string.

    Veja bem, preste atenção!

    O using namespace std; traz para o programa todos os nomes da biblioteca padrão, que são milhares. Isso aumenta a chance de conflito com nomes que você mesmo criou: uma variável ou função chamada count, max, distance ou size, por exemplo, pode passar a colidir com uma função da biblioteca padrão de mesmo nome, gerando erros de compilação difíceis de entender, ou pior, chamando a função errada sem aviso.

    Em programas pequenos, de um único arquivo, o risco é pequeno e muita gente usa. Em arquivos de cabeçalho (.h/.hpp), porém, ele nunca deve ser usado, porque o efeito se espalha para todos os arquivos que incluírem aquele cabeçalho.

    Um meio-termo é trazer apenas os nomes que você vai usar:

    using std::cout;
using std::string;

    Neste texto, os exemplos sempre usam o prefixo std:: explicitamente. Assim, fica claro o que vem da biblioteca padrão e o que foi definido no próprio programa.

    Edição do código fonte¶

    Analisando friamente, podemos utilizar qualquer editor de textos para escrever um programa em C++ (ou em qualquer outra linguagem). O problema é que a nossa produtividade (linhas de código que escrevemos pelo esforço despendido) não vai ser boa.

    Um editor de texto está preparado para editar qualquer tipo de texto. Ele não foi pensado para escrever programas, então faltam algumas coisas importantes, como a integração com um compilador, um ambiente para executar o programa e ferramentas para auxiliar a resolver erros que aparecem durante a compilação ou a execução. O ideal é que façamos o desenvolvimento dentro de um IDE.

    Um Ambiente Integrado de Desenvolvimento (IDE, do inglês Integrated Development Environment) é um software que reúne diversas ferramentas essenciais para a programação em um único local. Ele geralmente inclui um editor de código, um compilador, um depurador e outros recursos que auxiliam na escrita, teste e manutenção do código.

    O uso de IDEs durante o aprendizado de programação gera debates entre desenvolvedores e educadores. Por um lado, elas oferecem realce de sintaxe, autocompletar, indicação de erros enquanto digitamos e depuração integrada, o que acelera o desenvolvimento. Por outro lado, recursos como autocompletar e sugestões automáticas podem fazer com que o estudante não compreenda completamente a sintaxe e a lógica por trás do código, e a dependência excessiva da ferramenta pode criar dificuldades quando for preciso trabalhar em ambientes mais simples. Uma abordagem equilibrada é usar a IDE pelo que ela tem de melhor (a integração entre editor, compilador e depurador), sem deixar que ela escreva o programa por você.

    Para C++, há um cuidado adicional: a versão do compilador importa. Os exemplos deste texto usam recursos do padrão C++20, que exigem o GCC na versão 13 ou mais recente (e alguns recursos de C++23, sempre indicados, exigem o GCC 14). Algumas IDEs populares entre iniciantes trazem compiladores antigos embutidos e não vão conseguir compilar parte dos exemplos. Algumas combinações que funcionam bem são:

    • Visual Studio Code com a extensão C/C++, usando um compilador GCC recente. No Windows, o GCC pode ser instalado por meio do MSYS2; no Linux, ele está disponível no gerenciador de pacotes da distribuição, e;
    • CLion, da JetBrains, que é gratuito para uso não comercial e educacional.

    Qual é a versão do meu compilador?

    Abra um terminal e digite g++ --version. A primeira linha da resposta mostra a versão. Com a versão 13 ou mais recente, todos os exemplos em C++20 deste texto funcionam; os recursos de C++23 indicados no texto exigem a versão 14.

    Na Maratona SBC de Programação e no ICPC, os programas são compilados com o GCC 13.2 em C++20. No Arena, com o GCC 14.2 e a linha de comando g++ -std=c++23 -O2. A seção C++20 e C++23 detalha o que muda entre esses ambientes.

    Comentários¶

    Os comentários são elementos não executáveis que fornecem descrições e explicações adicionais dentro do código fonte. Eles desempenham um papel fundamental na documentação do programa, tornando-o mais legível e compreensível tanto para o próprio desenvolvedor quanto para outros programadores que possam trabalhar com o código no futuro.

    A linguagem C++ suporta dois tipos de comentários.

    O primeiro tipo são os comentários de linha única, que começam com duas barras (//) e se estendem até o final da linha. Tudo o que estiver após essas duas barras será ignorado pelo compilador.

    // Este é um comentário de linha única
int idade = 18;  // Comentários também podem vir depois do código

    O segundo tipo são os comentários de múltiplas linhas, também conhecidos como comentários em bloco. Eles começam com a sequência /* e terminam com */. Todo o texto entre esses delimitadores é considerado comentário, independentemente de quantas linhas ele ocupe.

    /* Este comentário pode se estender por várias
   linhas e explicar detalhadamente o funcionamento
   de determinado trecho de código */

    Os comentários são utilizados por diversas razões importantes no desenvolvimento de software:

    • Eles tornam o código mais legível para referência futura, o que é especialmente útil quando o programador precisa revisitar seu próprio código após um longo período;
    • Os comentários são ferramentas valiosas para depuração, permitindo que partes do código sejam temporariamente desativadas para testes, e;
    • Em ambientes onde múltiplos desenvolvedores trabalham no mesmo projeto, comentários bem escritos facilitam o entendimento do código por todos os membros da equipe, principalmente em códigos complexos ou otimizados, onde a lógica pode não ser imediatamente óbvia.

    Veja bem, preste atenção!

    Os comentários não devem ser usados como substitutos para código mal escrito. A prioridade deve ser sempre escrever código limpo e compreensível, utilizando comentários como complemento para esclarecer intenções e lógicas complexas.

    Para utilizar comentários de forma eficaz, é recomendado que eles expliquem o "porquê" por trás do código, não apenas o "como". Comentários devem ser claros e concisos, fornecendo informações suficientes para entender o propósito do código sem serem excessivamente detalhados.

    É importante manter os comentários atualizados quando o código é modificado. Comentários desatualizados podem causar confusão e levar a erros de interpretação. Além disso, deve-se evitar comentários redundantes, que apenas repetem o que o código já expressa claramente.

    Pré-processamento¶

    graph LR
  Fonte1 --> Preprocessamento1 --> Processado1
  Cabecalhos --> Preprocessamento1

  Fonte1@{ shape: doc, label: "**Código fonte**<br />(.cpp)" }
  Cabecalhos@{ shape: docs, label: "**Arquivos de cabeçalho**<br />(.h, .hpp)" }
  Preprocessamento1@{ shape: process, label: "Pré-processamento" }
  Processado1@{ shape: doc, label: "**Código pré-processado**<br />(.ii)" }

    A segunda etapa é o pré-processamento, feita pelo pré-processador, um programa que "prepara" o código antes da compilação propriamente dita. As instruções para o pré-processador são chamadas de diretivas e começam sempre com #.

    Durante esta fase:

    • Os arquivos de cabeçalho são incluídos no arquivo fonte;
    • As macros são expandidas;
    • Os trechos de compilação condicional são mantidos ou descartados, e;
    • Os comentários são eliminados.

    O resultado é uma versão "limpa" do código fonte, normalmente com extensão .ii, que contém o código original mais o conteúdo de todos os arquivos incluídos. Esse arquivo é muito maior que o original: o "Olá, mundo!" da seção anterior, que tem 7 linhas, vira um arquivo com dezenas de milhares de linhas depois do pré-processamento, porque o cabeçalho <iostream> inclui muitos outros.

    As principais diretivas do pré-processador são:

    • #include: inclui o conteúdo de outro arquivo no ponto em que a diretiva aparece. Com sinais de menor e maior (#include <vector>), o arquivo é procurado nos diretórios da biblioteca padrão e do sistema. Com aspas (#include "funcoes.hpp"), ele é procurado primeiro no diretório do próprio projeto;

    • #define: define uma macro, que é uma substituição de texto. Se usarmos, por exemplo, #define PI 3.14159, o pré-processador substituirá todas as ocorrências de PI no código por 3.14159. Ao fazermos #define QUADRADO(x) ((x) * (x)), o pré-processador substitui as ocorrências de QUADRADO(valor) por ((valor) * (valor)) antes da compilação. A diretiva também pode ser usada apenas para definir um símbolo (#define DEBUG), cuja existência pode ser verificada depois (#ifdef DEBUG);

    • #undef: remove a definição de um símbolo ou macro. A partir deste ponto, o pré-processador não conhece mais aquele nome, e;

    • #ifdef, #ifndef, #if, #else e #endif: permitem compilar trechos do código apenas se determinada condição for satisfeita. Isso é útil, por exemplo, para incluir mensagens de depuração apenas durante o desenvolvimento, ou para escrever um programa que use bibliotecas diferentes dependendo do sistema operacional.

    #include <iostream>

#define DEBUG

int main()

    int lado = 7;

    Se a linha #define DEBUG for removida (ou comentada), a mensagem de depuração simplesmente deixa de existir no programa compilado, sem que seja preciso apagar a linha que a escreve.

    Veja bem, preste atenção!

    Macros são substituições de texto feitas antes da compilação, sem nenhuma verificação de tipo, e isso pode produzir resultados surpreendentes. No exemplo abaixo, QUADRADO(a++) vira ((a++) * (a++)), ou seja, a variável a é incrementada duas vezes na mesma expressão, o que deixa o resultado indefinido (o próprio compilador emite um aviso). A função quadrado não tem esse problema: o argumento é avaliado uma única vez e só depois o valor é passado para a função.

    Incorreto

    #define QUADRADO(x) ((x) * (x))

int a = 3;
int r = QUADRADO(a++);  // ((a++) * (a++)): resultado indefinido

    Correto

    constexpr int quadrado(int x)
{
    return x * x;
}

int b = 3;
int r = quadrado(b++);  // r = 9 e b = 4

    Em C++, use constexpr para constantes e funções no lugar de macros. Reserve o #define para a compilação condicional e para as proteções de cabeçalho, apresentadas a seguir.

    Proteção contra inclusão múltipla¶

    Em um projeto com vários arquivos, é comum que um mesmo cabeçalho acabe sendo incluído mais de uma vez no mesmo arquivo fonte (por exemplo, quando dois cabeçalhos diferentes incluem um terceiro). Isso faria com que as mesmas declarações aparecessem repetidas, gerando erros de compilação. Para evitar o problema, todo arquivo de cabeçalho deve ter uma proteção de inclusão (include guard):

    geometria.hpp
    1
2
3
4
5
6
7
    #ifndef GEOMETRIA_HPP
#define GEOMETRIA_HPP

double area_circulo(double raio);
double area_quadrado(double lado);

#endif // GEOMETRIA_HPP

    Na primeira vez que o cabeçalho é incluído, o símbolo GEOMETRIA_HPP ainda não existe; o pré-processador então o define e mantém o conteúdo. Nas vezes seguintes, o símbolo já existe e todo o conteúdo entre #ifndef e #endif é descartado.

    Os compiladores atuais também aceitam a diretiva #pragma once no início do cabeçalho, que tem o mesmo efeito em uma única linha. Ela não faz parte do padrão da linguagem, mas é suportada por todos os compiladores mais usados.

    Compilação e montagem¶

    graph LR
  Processado1 --> Compilador1 --> Obj1

  Processado1@{ shape: doc, label: "**Código pré-processado**<br />(.ii)" }
  Compilador1@{shape: process, label: "Compilação e montagem" }
  Obj1@{ shape: doc, label: "**Código objeto**<br />(.o)" }

    Nesta etapa, o compilador realiza a análise sintática e semântica do código pré-processado. Ele verifica se o código está escrito corretamente, seguindo as regras da linguagem C++: parênteses não fechados, falta de ponto e vírgula, uso de variáveis não declaradas, tipos incompatíveis, entre outros erros.

    Se não houver erros, o compilador traduz o código para a linguagem de montagem da máquina (linguagem assembly), que é uma representação de baixo nível mais próxima da linguagem de máquina, com instruções específicas para a arquitetura do processador (como x86 ou ARM) em que o programa vai ser executado. O resultado é, normalmente, um arquivo com extensão .s.

    A etapa de montagem transforma o código assembly em código objeto, que já está em linguagem de máquina, porém ainda não pode ser executado: ele pode depender de funções ou variáveis definidas em outros lugares (em outro arquivo .cpp ou em bibliotecas). Cada arquivo .cpp gera seu próprio arquivo objeto, de extensão .o. A parte do compilador que faz essa conversão é o montador, ou assembler.

    Na prática, não executamos cada etapa separadamente: um único comando faz o pré-processamento, a compilação, a montagem e a link-edição. Com o GCC, o compilador de C++ é chamado de g++:

    g++ -std=c++20 -Wall -Wextra -o ola ola.cpp

    Cada parte do comando tem um papel:

    • -std=c++20: indica a versão do padrão da linguagem que deve ser usada. Sem essa opção, o compilador usa uma versão padrão, que varia de acordo com a versão do próprio compilador;
    • -Wall -Wextra: ativam a maior parte dos avisos (warnings) do compilador. Um aviso não impede a geração do programa, mas indica um trecho de código suspeito, que provavelmente contém um erro;
    • -o ola: define o nome do arquivo executável gerado (no Windows, ola.exe), e;
    • ola.cpp: o arquivo fonte a ser compilado.

    Leve os avisos a sério

    Os avisos do compilador são uma das ferramentas mais eficientes para encontrar erros antes mesmo de executar o programa. Compile sempre com -Wall -Wextra e trate cada aviso como um erro a ser corrigido: na grande maioria das vezes, o compilador está certo.

    Vendo cada etapa separadamente

    É possível pedir ao g++ que pare depois de cada etapa, o que ajuda a entender o processo:

    • g++ -E ola.cpp -o ola.ii: só o pré-processamento;
    • g++ -S ola.cpp: pré-processamento e compilação, gerando o assembly (ola.s);
    • g++ -c ola.cpp: pré-processamento, compilação e montagem, gerando o código objeto (ola.o), e;
    • g++ ola.o -o ola: só a link-edição, a partir do código objeto.

    Link-edição¶

    graph LR
  Obj1 --> Link --> Exec
  Bib1 --> Link

  Obj1@{ shape: doc, label: "**Código objeto**<br />(.o)" }
  Bib1@{ shape: lin-doc, label: "**Bibliotecas**<br />(libstdc++, .a, .so, .dll)" }
  Link@{ shape: process, label: "Link-edição" }
  Exec@{ shape: doc, label: "**Programa executável**<br />(.exe)" }

    Imagine que os arquivos objeto são como peças de um quebra-cabeça: cada um tem uma parte do programa, mas eles precisam ser conectados para formar o todo. A link-edição é a etapa final do processo, em que o linkeditor (linker) combina todos os arquivos objeto gerados e as bibliotecas necessárias em um único arquivo executável. O linker realiza as seguintes tarefas:

    • Resolve as referências entre os diferentes arquivos objeto do programa, garantindo que toda função ou variável usada em um arquivo esteja definida em algum lugar;
    • Adiciona ao executável o código das bibliotecas usadas pelo programa. Em C++, a mais importante é a implementação da biblioteca padrão (no GCC, chamada de libstdc++), onde estão std::cout, std::string e todos os outros recursos do espaço de nomes std. O comando g++ já inclui essa biblioteca automaticamente, e;
    • Gera o arquivo executável final.

    Se alguma função foi declarada e usada, mas não foi definida em nenhum arquivo objeto ou biblioteca, o linker interrompe o processo com um erro de "referência indefinida" (undefined reference). Esse erro aparece mesmo quando o código de cada arquivo está correto, porque o problema não está em nenhum arquivo isolado, e sim na ligação entre eles.

    O arquivo gerado ao final pode ser executado diretamente pelo sistema operacional.
